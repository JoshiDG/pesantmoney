**Purpose:** input for a UI redesign design decision for PesantMoney. Investigates three historical desktop UI guideline systems against primary sources (official specs, archived guideline documents, first-party docs) rather than blog summaries.

## System 1: IBM Common User Access (CUA)

### (a) Philosophy / principles

The primary 1989 document I obtained and read directly — **"Systems Application Architecture: Common User Access — Basic Interface Design Guide", Document Number SC26-4583-00, First Edition, December 1989, Copyright IBM Corp. 1989** (full text via Internet Archive, see sources) — repeatedly uses the term **"walk-up-and-use"** for its target usability bar, e.g.: *"walk-up-and-use, because it leads users through a simple series of tightly [structured choices]"* and *"An application that is designed to be walk-up-and-use by users who are..."* (lines ~1688, 4240 of the OCR text). This matches the paraphrase in a 2024 Register retrospective, which characterizes CUA's goal as *"a 'walk up and use' design, where someone who has never seen a program before can operate it first time"* — but I now have this directly from the primary document, not just the secondary paraphrase, so this is **well-documented**.

The Register retrospective (Liam Proven, *"The rise and fall of the standard user interface,"* The Register, 24 Jan 2024) additionally states CUA's scope was broader than GUIs: *"CUA proposed a set of principles on how to design a user interface: not just for GUI or OS/2 apps, but all user-facing software, including text-only programs, even on mainframe terminals."* and that CUA *"didn't assume the computer had a mouse."* This matches what I found directly in SC26-4583-00 — the document explicitly covers both a **"nonprogrammable terminal"** (text-mode 3270-style) and a **"programmable workstation"** (PC/PM-style with a mouse) as two renderings of the same interaction model. **Well-documented** (both primary text and reputable retrospective agree, and the primary text's own structure confirms it).

Note on legal context: the Register piece situates CUA's 1987-88 emergence alongside the Apple v. Microsoft, Apple v. Digital Research, and Lotus v. Paperback look-and-feel lawsuits, suggesting IBM's timing was partly about establishing a non-Apple-derived standard. This is the Register author's historical interpretation/argument, not something I could independently verify from IBM's own documents — flagged as **reconstructed/inferred**.

### (b) Concrete conventions

From the primary SC26-4583-00 text I read directly:

- **Menu/mnemonic distinction (a real, documented terminology, not the modern Windows Alt/Ctrl split):** *"The programmable workstation supports mnemonic selection... A mnemonic is a single character that provides a fast interaction technique for selecting choices from the keyboard. When users type a valid mnemonic, the selection cursor moves to the choice... A mnemonic is underlined to provide a visual cue..."* (§2.7.1). Separately: *"You may assign function keys to the choices in a pull-down. These function keys are called accelerators."* (§ near line 9357) — in CUA-89, **"accelerator" means a function key (F1–F24) bound to a menu action**, working whether or not the pull-down is open, distinct from a "mnemonic" (a single letter used to navigate/select within an open menu or field). This is notably **different from the later Windows convention** where "accelerator" commonly means a Ctrl+letter combo and "mnemonic" means Alt+underlined-letter — that later, more familiar split is associated with CUA-91 and Windows/PM's graphical extensions, but I could not find CUA-91's own primary text online to confirm its exact wording (see Known Gaps). **Well-documented for CUA-89 specifically; the CUA-91/Windows terminology shift is reconstructed/inferred from secondary sources** (Wikipedia's "IBM Common User Access" article, retrieved via WebFetch, states: "Menus are opened by pressing the Alt key plus the underlined letter" and lists Cut=Shift+Del, Copy=Ctrl+Ins, Paste=Shift+Ins, F1=context help, F10=menu activation — but Wikipedia does not cite a specific document edition for these, so I treat this as **reconstructed/inferred**, not primary-sourced).

- **Mnemonic assignment rule**, quoted directly from §2.7.4 "Programming Considerations": *"In each window, a mnemonic must be unique within the action bar, within a pull-down, and within the client area. If possible, assign the first letter of a choice as its mnemonic... Choices that appear many times in an application should always be assigned the same mnemonic."* **Well-documented.**

- **Menu bar / action bar structure**: the guide calls the menu bar the **"action bar."** *"Exit in Pull-Down: The Exit action should always be the last choice in the first (farthest left) pull-down. If you use the standard action bar choices, Exit will be the last action in the File pull-down."* Wikipedia's summary (cross-checked, not primary) adds that the first menu is conventionally "File" and the last is "Help" — consistent with what the primary source implies about Exit being last in File, though I did not find the primary text's exact statement that Help must be the rightmost action-bar item; treat that specific claim as **reconstructed/inferred** (Wikipedia only).

- **Dialog/message-box conventions**: *"Messages are displayed in pop-ups... These pop-ups are referred to as message boxes in OS/2. The pop-up is positioned so it does not cover the field in which the error occurred. Pushbuttons are located at the bottom of the pop-up. The cursor is positioned on the OK pushbutton. Users can press the Enter key or click on the OK pushbutton..."* and *"Users can select Cancel or Help at any time during the dialog."* This documents: buttons at the bottom, default focus on OK, Enter activates OK, Cancel/Help available throughout. **Well-documented** — directly quoted from SC26-4583-00.

- **Layout constraint** (§2.7.4, item 2): *"Avoid using the full width of the panel because there must be room for the scroll bar on the right side of the screen. Do not use more than 76 columns for a panel so that the scroll bar will be visible..."* — a concrete, primary-sourced spacing/layout rule, though specific to the text-mode "nonprogrammable terminal" context rather than a pixel-grid GUI rule. **Well-documented** for that context; I found no equivalent pixel/grid spacing rule for the graphical (PM) rendering in the material I could access.

### (c) Sources and confidence

- Primary: **"CUA Basic Interface Design Guide," SC26-4583-00, First Edition, December 1989, © IBM Corp.** Full OCR'd text retrieved from Internet Archive: https://archive.org/details/ibm-saa-cua-basic-interface-design-guide (file `IBM SAA - CUA Basic Interface Design Guide_djvu.txt`). I read this text directly (not a summary). **Well-documented** for everything cited to it above.
- Secondary/retrospective: Liam Proven, "The rise and fall of the standard user interface," *The Register*, 24 Jan 2024, https://www.theregister.com/2024/01/24/rise_and_fall_of_cua/ — used for historical/legal context and the "walk up and use" framing (cross-confirmed against the primary text) and OS lineage claims (Windows 3.0 borrowing from OS/2 1.2 Program Manager/File Manager; CDE and Xfce as CUA-descended; GNOME 2 vs GNOME 3 divergence). These lineage/adoption claims are **the Register author's own historical account** — I did not independently verify e.g. the Windows 3.0/OS/2 1.2 code-lineage claim against a primary Microsoft or IBM source, so flag as **reconstructed/inferred**.
- Secondary: Wikipedia, "IBM Common User Access," https://en.wikipedia.org/wiki/IBM_Common_User_Access — used for the Alt+underline / Ctrl+ combo claims and document-edition list (SC26-4351-00 1987 "Panel Design and User Interaction"; SC26-4582-00 1990 "Advanced Interface Design Guide"; SC34-4289-00 and SC34-4290-00, both 1991; SC34-4399-00 Dec 1992 "Object-Oriented Interface Design," stated to supersede the 1991 guides). **Reconstructed/inferred** — I could not access any of these other editions' primary text to verify Wikipedia's summary of them (only the 1989 Basic guide was accessible as full text).
- Secondary: EDM2 wiki page on Common User Access, https://www.edm2.com/index.php/Common_User_Access — corroborates the edition list above; does not add verifiable detail beyond it.

### CUA-89 vs. CUA-91

I could **not** locate primary full text for either the 1990 "Advanced Interface Design Guide" (SC26-4582-00) or the 1991 documents (SC34-4289-00, SC34-4290-00). Every source I found that claims specific CUA-89-vs-CUA-91 differences (e.g., that CUA-91 introduced the graphical Alt-underline/Ctrl-combo split, or added object-oriented/Workplace Shell concepts) is a **secondary paraphrase** (Wikipedia, a WebSearch AI-generated summary), not a document I could read directly. I am explicitly flagging this as **reconstructed/inferred, not verified** — the one specific, testable claim I *could* check (the 1989 Basic guide's own mnemonic/accelerator terminology) turned out to differ from what's commonly described as "the CUA convention" (Alt+letter / Ctrl+letter), which is itself evidence that the commonly-repeated summary conflates editions.

## System 2: QNX Photon microGUI

### (a) Philosophy / principles

**This section is thin, and I am stating that plainly rather than padding it.** I searched specifically for a Photon *design-philosophy* document (as distinct from API/widget reference material) and did not find one. What exists and is verifiable:

- QNX's own architecture documentation (multiple versions, e.g. the QNX 4 "System Architecture" book and the QNX Neutrino "System Architecture" book, both hosted at qnx.com) describes Photon in *systems-architecture* terms, not *user-experience* terms: *"The Photon microkernel runs as a tiny process, implementing only a few fundamental primitives that external, optional processes use to construct the higher-level functionality of a windowing system,"* and *"Photon differentiates itself by restricting the functionality implemented within the graphical microkernel (or server) itself and distributing the bulk of the GUI functionality among the cooperating processes."* This is a **software-architecture philosophy** (microkernel-style decomposition, scalability up/down for embedded use), explicitly **not** a stated user-interaction philosophy comparable to CUA's "walk-up-and-use" or Apple's ten principles. **Well-documented as architecture philosophy; explicitly absent as UX philosophy** — I did not manufacture UX principles to fill the gap.
- The Photon Programmer's Guide describes the widget model in OOP terms: *"you don't have to know the implementation details of a widget to use it — you just need to know the public interface for the widget"* (encapsulation) and recommends **PhAB (Photon Application Builder)**, a visual/RAD tool, as the standard way to assemble UIs from a widget palette, rather than hand-coding widget management.

I found no equivalent of a "Photon Human Interface Guidelines" document analogous to Apple's HIG or CUA's design guides. If such a document existed inside QNX Software Systems it does not appear to be publicly archived at the URLs I could reach.

### (b) Concrete conventions

What I could verify, all from **widget/API reference documents**, not a style guide:

- **PtMessage widget** (message/dialog box widget), from the QNX Photon 1.14 widget reference: up to three buttons, positioned **below the message**; *"Button 1 defaults to 'Ok' if no label is provided; buttons 2 and 3 default to NULL"* (not displayed unless labeled); a `Pt_ARG_MSG_DEFAULT` resource designates which numbered button is the default, selectable by pressing **Enter**, and *"the text of the default button is displayed in bold"* — button 1 is the default default. A `Pt_ARG_MSG_ESCAPE` resource binds Escape to trigger a specific button's callback. Keyboard mnemonics for buttons are assignable using an `&` prefix character in the label string (e.g., `"&OK"`), analogous to Windows' `&` mnemonic markup. Default font for the widget is Helvetica 12pt. `Pt_MSG_CENTER_ON_PARENT` centers the dialog on its parent. **Well-documented** (direct widget-reference quotes), but note this is a **widget class's configurable defaults**, not a prescriptive human-interface *rule* that all Photon apps must follow — Photon's docs don't say "dialogs must have OK on the right" the way CUA and Apple's HIG do; they describe what one particular widget class does by default.
- I found no documented standard for menu-bar structure (no equivalent of CUA's "File first, Help last" rule) or for keyboard mnemonic-vs-accelerator conventions at the *application design* level (as opposed to the single `&`-prefix widget feature above) in the material I could access.
- No documented spacing/grid/layout rules were found (PhAB is a visual/drag-and-drop builder, and the docs describe it as a tool rather than prescribing a grid).

### (c) Sources and confidence

- QNX Neutrino "System Architecture" (Photon chapter): https://www.qnx.com/developers/docs/6.4.0/photon/prog_guide/intro.html and https://www.qnx.com/developers/docs/qnx_4.25_docs/qnx4/sysarch/photon.html — **well-documented** for the architecture-philosophy quotes above (both fetched and quoted directly).
- QNX Photon Programmer's Guide (multiple versions cross-linked from qnx.com): confirms PhAB-centric, callback-driven, widget-encapsulation design approach. **Well-documented** for what it states; explicitly does not contain UX-principle content.
- PtMessage widget reference, QNX Photon 1.14: http://www.qnx.com/developers/docs/qnx_4.25_docs/photon114/widget_ref/ptmessage.html — **well-documented**, directly quoted.
- Absence claim ("no design-philosophy document found," "no menu-bar standard found"): based on targeted WebSearch queries across qnx.com documentation trees (versions 4.25, 6.1, 6.3.x, 6.4.x, 6.5.x) and general web search for "Photon style guide" / "Photon UI guidelines" — I could not access a QNX account/download-gated area (one QNX download link redirected to a login wall I did not attempt to bypass), so it remains possible a style guide exists behind that gate. I'm flagging this explicitly rather than asserting the document definitely doesn't exist anywhere.

**This is the weakest-sourced of the three systems** — not because I under-researched it, but because the primary-source material genuinely doesn't contain a stated design philosophy, and I'm reporting that absence rather than inventing one.

## System 3: Apple Human Interface Guidelines (1987)

### (a) Philosophy / principles

I obtained and read the **actual 1987 text directly**: *"Human Interface Guidelines: The Apple Desktop Interface," Copyright © 1987 by Apple Computer, Inc., Addison-Wesley Publishing Company* (digitized copy via Internet Archive, https://archive.org/details/applehumaninterfOOappl, full text extracted from the PDF at https://andymatuschak.org/files/papers/Apple%20Human%20Interface%20Guidelines%201987.pdf). This is distinct from — and should not be confused with — the later 1992/1995 *"Macintosh Human Interface Guidelines"* (a different, later book; I initially mis-fetched a copy of that later edition and confirmed the mismatch by checking its copyright page, which reads "© 1995, Apple Computer, Inc.").

Chapter 1, "Philosophy," states verbatim: *"This section describes the ten fundamental principles of the Apple Desktop Interface."* The ten, quoted directly with their exact stated one-line definitions:

1. **Metaphors from the real world** — *"Use concrete metaphors and make them plain, so that users have a set of expectations to apply to computer environments."*
2. **Direct manipulation** — *"Users want to feel that they are in charge of the computer's activities."*
3. **See-and-point (instead of remember-and-type)** — *"Users select actions from alternatives presented on the screen... Users rely on recognition, not recall."*
4. **Consistency** — *"Effective applications are both consistent within themselves and consistent with one another."*
5. **WYSIWYG (what you see is what you get)** — *"There should be no secrets from the user, no abstract commands that only promise future results."*
6. **User control** — *"The user, not the computer, initiates and controls all actions."*
7. **Feedback and dialog** — *"Keep the user informed. Provide immediate feedback."*
8. **Forgiveness** — *"Users make mistakes; forgive them. The user's actions are generally reversible — let users know about any that aren't."*
9. **Perceived stability** — *"Users feel comfortable in a computer environment that remains understandable and familiar rather than changing randomly."*
10. **Aesthetic integrity** — *"Visually confusing or unattractive displays detract from the effectiveness of human-computer interactions."*

All ten term names above are **verified exact terms from the document itself**, not a reconstruction — this fully confirms the candidate list given in the research brief (metaphors, direct manipulation, see-and-point, consistency, WYSIWYG, forgiveness, feedback/dialog, user control all appear verbatim; the brief's "perceived stability" and "aesthetic integrity" are also both exact). A closely related eleventh concept, **"Modelessness,"** is described in the same chapter under a "programming strategy" subsection (not one of the ten numbered principles, but presented immediately after them): *"With few exceptions, a given action on the user's part should always have the same result, irrespective of past activities."* **Well-documented — directly quoted from the primary 1987 text.**

### (b) Concrete conventions

All quotes below are directly from the 1987 primary text unless noted otherwise:

- **Menu bar structure**: *"Three of the menus — the Apple menu, the File menu, and the Edit menu — are standard menus that appear as the first... menus in almost every application. When making up your own menus, do not give them the same names as standard menus."* The **Apple menu** (also called the "desk accessory menu") is *"always the leftmost menu"* and lists installed desk accessories. The **File menu** handles *"opening, closing, saving, and printing... A key item in the File menu is the Quit operation, which lets the user quit an application at any time"* (explicitly contrasted with older software requiring return to a "Main Menu" to quit). The **Edit menu** rule is explicit and prescriptive: *"Every application should include an Edit menu with Undo, Cut, Copy, Paste, and Clear (in that order). Even if the application itself doesn't use them, those five commands must be available for desk accessories that may need them."* **Well-documented.**
- **Dialog box layout rule**, quoted directly: *"In general, dialog boxes should be laid out with the most important information and controls at the top left, working down to the less important information, ending with the default button — the button most likely to be clicked — at the lower right. In Western countries, people are used to reading and writing from left to right and top to bottom, so this is the most natural way to fill in information."* This is a **top-left → bottom-right importance/reading-order rule**, explicitly tied to the default button's position (lower right). **Well-documented — directly quoted.**
- **Modal vs. modeless dialogs**, quoted directly: *"A modal dialog box is one that the user must explicitly dismiss before doing anything else... A modal dialog box usually has at least two buttons: OK and Cancel. OK dismisses the dialog box and performs the original command... Cancel dismisses the dialog box and cancels the original command. It should always be called Cancel."* *"The default button (the most likely choice in the current situation) is doubly outlined to call attention to it. It is usually in the lower-right corner of the box... The user can activate the default button simply by pressing Return or Enter."* *"A modeless dialog box allows the user to perform other operations without dismissing the dialog box... dismissed by clicking in the close box or by choosing Close... buttons never dismiss the dialog box. In this context, the OK button means 'go ahead and perform the operation, but leave the dialog box up,' whereas the Cancel button usually terminates an ongoing operation."* **Well-documented — this is a fully specified, directly-quoted convention**, including the concrete figure example (a modal dialog with buttons ordered **Cancel, then OK**, left-to-right, with OK as the doubly-outlined default on the right).
- **Ellipsis convention**: *"A dialog box appears whenever the user chooses a menu item that is followed, in the menu itself, by an ellipsis (...)."* **Well-documented.**
- **Keyboard equivalents ("Command-key" shortcuts)**: the 1987 document's own term is **"keyboard equivalents"**, using the **Apple/Command key** (labeled with an Apple symbol or cloverleaf/"Open Apple" symbol) plus a character key — e.g., Command-Q for Quit, Command-S for Save. Crucially, the document explicitly frames these as *secondary to*, not a replacement for, the see-and-point/mouse model: *"It is essential, however, that keyboard equivalents offer an alternative to the see-and-point approach — not a substitute for it."* On the letter-choice rule: *"The letter used for a keyboard equivalent should be mnemonic — it should either be the first letter of the command... or it should have some other relevance (X for Cut, for example)."* A standard table is given: Apple-menu Help = Command-?; File menu: Command-N (New), Command-O (Open), Command-S (Save), Command-Q (Quit); Edit menu: Command-Z (Undo), Command-X (Cut), Command-C (Copy), Command-V (Paste). Note there is **no Alt-key/underlined-letter menu-navigation mnemonic system** in this document at all (unlike CUA) — classic Mac menus are opened by mouse only in this 1987 spec; "mnemonic" here refers only to the *letter chosen* for a Command-key shortcut, not to a keyboard-driven menu-opening mechanism. **Well-documented — directly quoted, and the absence of an Alt+underline convention is a positive, checkable finding, not an assumption.**
- **Typography (Chicago/Geneva)**: I searched specifically for the brief's suggested Chicago/Geneva usage guidance and **did not find an explicit prescriptive rule in the 1987 text itself** (e.g., "use Chicago for menu bar text, Geneva for icon labels"). What the document does contain: a Font menu example figure listing available system fonts including **Chicago, Geneva, Athens, London, Monaco, New York, Venice** as example choices a user could select for document text — i.e., the 1987 HIG's typography content is about *how the Font/FontSize/Style menus should work for user-facing document text* (points, fixed-width vs. proportional, serif vs. sans-serif), not about which system font the OS chrome itself should use. The fact that Chicago was the fixed system UI font (menus, dialogs, window titles) is a well-established fact about classic Mac OS more broadly (confirmed via Wikipedia's "Chicago (typeface)" article, crediting designer Susan Kare, used from the 1984 launch through System 7.6), but I could not verify that the **1987 HIG document itself** states this as a rule — so I'm flagging the OS-level Chicago-as-system-font fact as **reconstructed/inferred** (true of the platform, per a secondary source, but not confirmed as a stated instruction inside the 1987 HIG document I read), while the Font-menu example figure is **well-documented** (directly present in the primary text).

### (c) Sources and confidence

- Primary: **"Human Interface Guidelines: The Apple Desktop Interface," © 1987 Apple Computer, Inc., Addison-Wesley** — full text obtained from https://andymatuschak.org/files/papers/Apple%20Human%20Interface%20Guidelines%201987.pdf (a digitization of the Internet Archive copy at https://archive.org/details/applehumaninterfOOappl). I converted this PDF to text locally (via `pdftotext`) and read the extracted text directly, including Chapter 1 "Philosophy" in full, the menu-bar and dialog-box sections of Chapter 2 "Elements of the Desktop Interface," and the dialog-box/keyboard-equivalents sections of Chapter 3 "Specifications." **Well-documented** for everything quoted above.
- Secondary (bibliographic cross-check only): GUIdebook, https://guidebookgallery.org/books/applehumaninterfaceguidelines — used only to corroborate edition/page-count/ISBN metadata (162–166 pp., Addison-Wesley, ISBN 0-201-17753-6); notes the book is sometimes catalogued as "third edition, published mid-1988, dated 1987 on the cover" — a minor discrepancy I could not resolve further (see Known Gaps).
- Secondary: Wikipedia, "Chicago (typeface)," used only for the OS-level system-font fact noted above (not verified against the 1987 HIG text itself).
- I also fetched (in error, then discarded for direct quotation purposes) a later **1992/1995** "Macintosh Human Interface Guidelines" PDF via a course-handout mirror at RWTH Aachen (https://apps.hci.rwth-aachen.de/borchers-old/cs377a/handouts/HIGuidelines.pdf) — its copyright page reads "© 1995, Apple Computer, Inc." This is a **different, later book** than the one the research brief asked about, and I have **not** used it for any claim above; I flag its existence only so a future reader doesn't confuse the two documents, since both circulate under very similar titles.

## System 4: NeXTSTEP (NeXT Computer)

### (a) Philosophy / principles

I obtained and read the primary document directly: **"NeXTSTEP User Interface Guidelines, Release 3," Part No. N6119, November 1993, NeXT Computer, Inc.** (scanned copy hosted on bitsavers.org via Internet Archive, https://archive.org/details/bitsavers_nextReleasInterfaceGuidelinesRelease3Nov93_9141848, PDF converted to text locally with `pdftotext` and read directly, not summarized). This is a Release 3 (1993) edition — I did not find a surviving full text of any earlier (1988–1990, original "NeXTSTEP" 0.x/1.0-era) edition, so all claims below are sourced to the 1993 document unless noted; treat this as **Release-3-specific**, analogous to the CUA-89-vs-91 caveat in System 1.

Chapter 2, "Design Philosophy," opens with a framing not unlike CUA's "walk-up-and-use" but phrased differently, quoted directly: *"A user interface must meet the needs of both novice and experienced users... The challenge is to accommodate both these goals in ways that don't conflict—to combine simplicity with efficiency."* It then states **four basic principles**, quoted verbatim: *"• The interface should be consistent across all applications. • The user is in charge of the workspace and its windows. • The interface should feel natural to the user. • The mouse (not the keyboard) is the primary instrument for user input."* Each is elaborated in its own subsection ("Consistency," "User Control," "Naturalness," "Using the Mouse"). **Well-documented — directly quoted from the primary 1993 text.**

A distinctive, explicitly-named concept not present in CUA or the 1987 Apple HIG: **"Modes,"** discussed under User Control, quoted directly: *"applications should avoid setting up arbitrary modes, periods when only certain actions are permitted... In the NeXTSTEP user interface, modes are used in only three situations: In the modal tool paradigm... In attention panels... In 'spring-loaded' modes that last only while the user holds a key or mouse button down."* This is a stronger, more explicit anti-modality stance than either CUA or the 1987 Apple HIG state outright (Apple's 1987 HIG discusses modal vs. modeless dialogs as a design choice; NeXTSTEP's text frames modes as inherently something to be minimized and justified). **Well-documented.**

The document also names three **"Action Paradigms"** governing all mouse interaction — **Direct Manipulation, Targeted Action, and Modal Tool** — quoted and defined directly (e.g., *"Most objects respond directly to manipulation with the mouse—a button is highlighted when pressed, a window comes forward when clicked..."* for Direct Manipulation; *"All controls have one thing in common: They act on a target"* for Targeted Action; *"users can change the meaning of subsequent mouse actions by selecting an appropriate tool, often displayed in a palette with several other tools"* for Modal Tool — the last of these is the primary-source description of a **floating tool palette**, matching the research brief's expectation). **Well-documented.**

### (b) Concrete conventions

- **Menu placement — "the Main Menu," upper-left, not a screen-edge-attached bar**: quoted directly from Chapter 4, "Implementing Standard Windows": *"When an application starts up, its main menu should appear in the upper left corner of the screen, unless the user has specified a different location for it. Standard windows should come up to the right of the main menu, allowing enough room for submenus that might later be attached to the main menu."* This confirms the brief's premise that NeXTSTEP's menu convention differs from a Windows/CUA-style bar fixed to the top edge of the display — the NeXTSTEP main menu is a **free-floating, user-movable, single vertical column of items** that defaults to the upper-left corner of the screen but is explicitly **not required to stay there or attach to any screen edge** ("unless the user has specified a different location for it"). I did not find, however, an explicit statement in this document that the main menu is conventionally placed along the **left edge of the screen** as a persistent vertical strip (as opposed to simply defaulting to the upper-left corner as a floating window) — the "left side of the screen" characterization in the research brief is **directionally correct but more precise than what this Release-3 text states outright**; I'm flagging the stronger "always on the left edge" framing as **reconstructed/inferred**, while "defaults to upper-left, user-repositionable, not attached to a screen edge" is **well-documented**.
- **The "Shelf"**: confirmed as a real, named UI element, but it is **not** a general desktop feature — it is specific to the **File Viewer** (the Workspace Manager's file-browser window), a strip where the user can drop folder/file icons for quick access. Quoted directly: *"An example of where dragging doesn't imply a single click is in the File Viewer shelf. When the user clicks the icon of a folder on the shelf, the File Viewer changes to show the folder's path. However, when the user drags the icon off the shelf, the File Viewer does not perform the click's action."* **Well-documented**, though the document treats it as one worked example of click-vs-drag disambiguation rather than devoting a full standalone section to the Shelf as a concept — I found no separate "Shelf" chapter/spec beyond this and one other passing reference.
- **Attention panels (the NeXTSTEP term for modal dialogs) — button placement and default rules**, quoted directly from Chapter 5, "Panels": *"The buttons that dismiss an attention panel should be located along the right and lower edges of the panel, with the default button in the lower right corner. No button except for the default button should be operable by the Return key."* And on labeling: *"generic labels (like Yes and No) aren't appropriate, as they tend to cause user errors. Avoid using OK unless it's the only button in the attention panel."* Good button names given directly in the text: "Cancel, Close Anyway, Don't Close, Don't Save, Explain, Open, Open Copy, Open Anyway, Quit Anyway, Replace, Revert, Review Unsaved, Save, Save All, Set." This is a **verb-phrase-button-label convention**, notably stricter than the 1987 Apple HIG's OK/Cancel convention. **Well-documented — directly quoted**, and notably this is close in spirit to (and may be an ancestor of) Apple's later Aqua-era "verb the noun" button-labeling guidance, though I did not attempt to verify a direct lineage claim.
- **Ordinary vs. attention panels**: an "ordinary panel" (e.g. the Font panel, an inspector) is non-modal — *"Ordinary panels let the user work in other windows and panels of the application while the panel is displayed."* An attention panel is explicitly modal to the application (but not system-wide): *"While an attention panel is displayed, the user can't do anything else in the application (although the user can work in other applications)."* This app-scoped (not system-scoped) modality is a specific, checkable design detail. **Well-documented.**
- **Window tiering** ("tiers"), from the glossary, quoted directly: *"The sections of the screen list. Each tier is occupied by a different type of window, with spring-loaded windows such as pop-up lists in the frontmost tier, attention panels in the second tier, menus in the next two tiers, docked icons in the tier below menus, and floating panels below docked icons. All other windows are in the bottom tier."* This is a **well-documented, seven-tier z-order model** — floating tool palettes ("floating panels") have their own dedicated tier, above ordinary document windows but below menus/attention panels/docked icons. **Well-documented.**
- **Typography / Display PostScript**: the document's own **Window Server** glossary entry states directly: *"A process that dispatches user events to applications and renders PostScript code on behalf of applications."* This confirms, from the primary UI-guidelines document itself (not a secondary retrospective), that the on-screen rendering pipeline is PostScript-based — consistent with NeXTSTEP's well-known use of **Display PostScript** for resolution-independent, WYSIWYG-with-print screen rendering. However, I want to flag precisely what I could and couldn't verify: **the phrase "Display PostScript" itself does not appear verbatim in this Release 3 UI Guidelines document** in the material I searched (it says "PostScript code," not the branded term); and I found **no prescriptive typographic spacing/grid rule** in this document analogous to CUA's "76 columns" rule or a stated system point-size grid — the only concrete font-related detail is an illustrative screenshot caption reading *"Helvetica Medium 18.0 pt."* for the Font panel example, plus a reference to `/NextLibrary/Fonts` as the shared system PostScript-fonts directory. So: **well-documented** that the rendering model is PostScript-based and resolution-independent by architecture (this is also extensively corroborated by NeXT's own separate technical/marketing literature and consistent secondary treatment, e.g. Wikipedia's NeXTSTEP article, which I did not need to rely on since the primary UI guide itself confirms the PostScript rendering fact) — but the specific claim that the *UI guidelines document prescribes* particular point sizes or a typographic grid is **not supported**; I'm reporting that absence rather than inventing a rule, the same honesty standard applied to QNX Photon's spacing gap in System 2.

### (c) Sources and confidence

- Primary: **"NeXTSTEP User Interface Guidelines, Release 3," Part No. N6119, November 1993, NeXT Computer, Inc.** Full scanned PDF via bitsavers.org, hosted at Internet Archive: https://archive.org/details/bitsavers_nextReleasInterfaceGuidelinesRelease3Nov93_9141848 (direct PDF: https://ia802807.us.archive.org/0/items/bitsavers_nextReleasInterfaceGuidelinesRelease3Nov93_9141848/NeXTSTEP_User_Interface_Guidelines_Release_3_Nov93.pdf). I downloaded this PDF, ran it through `pdftotext` locally, and read the resulting ~7,900-line extracted text directly — not a summary or a WebFetch-model paraphrase. **Well-documented** for everything quoted above.
- I additionally located, but did **not** use for direct quotation, the later **OpenStep User Interface Guidelines** (GNUstep-hosted PDF, https://www.gnustep.org/resources/documentation/OpenStepUserInterfaceGuidelines.pdf) — this is a related but distinct, later (post-NeXT/Sun OpenStep collaboration) document; noted here only so a future reader isn't confused between it and the NeXTSTEP Release 3 guide actually used.
- No secondary/retrospective sources were needed for the core conventions above since the primary Release 3 text directly covers philosophy, window/menu/panel conventions, and confirms the PostScript rendering architecture; where I could not confirm a claim from the brief (left-edge-attached menu strip; a prescriptive typographic grid) from this primary document, I have flagged it explicitly above as reconstructed/inferred or unsupported rather than treating the brief's framing as already-confirmed fact.

Philosophy, quoted/paraphrased from the fetched content: the document frames its goal around ease of use and target-audience focus — *"Haiku is an operating system which is known for its speed and being easy for anyone to use"* and *"Design your application to meet the needs of 80 percent of your target audience"* — an explicit **80%-of-users design target**, a more quantified framing than CUA's "walk-up-and-use" or Apple's ten principles, though I flag that I'm relying on a WebFetch-model extraction of this document rather than a locally-verified full-text read (unlike the CUA, Apple HIG, and NeXTSTEP sections above, I did not download and independently re-read this document's raw text with a text tool) — so treat the exact wording of these quotes as **moderately, not maximally, confident**; the substance (ease-of-use framing, 80%-target-audience principle) is consistent across the one fetch I performed and matches Be/Haiku's known performance-and-simplicity-conscious reputation, but I have not cross-verified the precise sentence boundaries against raw HTML/XML.

### (b) Concrete conventions

All drawn from the same Haiku HIG fetch (haiku-os.org/docs/HIG/index.xml), with the same provenance caveat as above:

- **Window types**: the document enumerates named window styles — *"Document"* (user documents, e.g. an editor or viewer), *"Titled"* (general purpose), *"Floating"* (tool/utility windows), *"Modal"* (modal windows), *"Bordered"* (alert-type dialogs), and *"Borderless"* (splash screens) — a more granular, explicitly-named taxonomy of window kinds than either CUA or the 1987 Apple HIG state. **Moderately well-documented** (single-fetch confidence, as noted above).
- **Standard menus**: *"Program"* (About, Settings, Quit), *"File"* (New, Open, Close, Save, Print), *"Edit"* (Undo, Redo, Cut, Copy, Paste) — plus, per the earlier search-result summary, Search and Help as further standard top-level menus. Guidance: *"Items should be organized and grouped by function and/or attribute"* and an explicit anti-example: *"a File menu should not have Copy and Paste items in it."* Notably, BeOS uses **"Program"** rather than an Apple-style leftmost app-identity menu or a CUA-style "File-first" rule — this is a distinct convention from both prior systems in this file. **Moderately well-documented.**
- **Alert/dialog conventions**: *"On a notification, such as an error message, use 'OK' for the label"*; guidance to avoid unnecessary confirmation prompts (*"Are you sure…"*) except for undoable destructive actions; and — matching NeXTSTEP's and diverging from a generic Yes/No pattern — explicit avoidance of generic Yes/No labels in favor of action-specific button text (e.g., "Save Changes/Discard Changes" per one fetch's paraphrase). This **echoes the NeXTSTEP verb-phrase-button convention** documented in System 4(b), though I did not find a citation in the Haiku document acknowledging that lineage — flagged as a **pattern observation, not a sourced lineage claim**.
- **Keyboard conventions**: the **Command key** (BeOS's Alt/Cmd-equivalent modifier, `B_COMMAND_KEY` in the API) is stated to be *"the main shortcut key,"* with a standard table: Command+N (new document), Command+O (open), Command+S (save), Command+Q (quit), Command+C/Command+V (copy/paste). An explicit prescriptive rule: *"Do not use one of the system combinations for a task different from the list… Doing so will only confuse and frustrate users"* — i.e., a **closed, reserved set of system-level shortcuts** that applications must not repurpose, similar in spirit to CUA's and Apple's reserved Edit-menu shortcuts. **Moderately well-documented.**
- I found **no specific spacing/grid/typography rule** in the material I could extract from this document (the fetch I performed did not surface one, and I did not have time within this pass to do a second, deeper fetch targeting a possible dedicated typography/layout chapter) — flagged as a **gap**, not as evidence such a rule doesn't exist; Haiku's HIG is a substantial multi-chapter document and I have only sampled it via one AI-summarized fetch rather than a full raw-text read.

## System 6: BlackBerry 10 (BB10) / Cascades UI framework

**Scope flag, per the research brief's own instruction:** BB10 is a **touch/gesture-based mobile** interaction model, unlike the other five systems in this file, which are desktop/pointer-and-keyboard systems. Menu bars, keyboard accelerators, and window-management conventions from Systems 1–5 mostly **do not translate** to this system. What follows is included for its **interaction-philosophy** value (navigation/flow patterns, information hierarchy, gesture-driven modality) rather than as a source of directly portable desktop conventions.

### (a) Philosophy / principles

I obtained and read directly the primary document: **"BlackBerry 10 UI Guidelines"** (official PDF, published by BlackBerry/Research In Motion for the Cascades native framework), retrieved from https://developer.blackberry.com/devzone/files/design/bb10/UI_Guidelines_BlackBerry_10.pdf, converted locally with `pdftotext` and read as extracted text directly (~3,600 lines), not summarized by an intermediary model. The document itself documents a **10.3-era visual refresh** (it opens with a "Version 10.3 visual refresh" changelog section covering simplified app icons and revised action bars), so this reflects a slightly later BB10 revision than the original 2013 launch, though the core "Key principles" chapter reads as the stable design philosophy across versions.

The document states six named **"Key principles,"** each with its own "What it is / Why it matters / Example / Best practice" structure, quoted directly:

1. **A fluid environment** — *"BlackBerry 10 provides a seamless experience that gives users full control and flexibility in every moment and with every touch. It's as natural and fluid as our actions are in the real world... Don't interrupt the flow between what users see and what they do next."* This is the primary-source statement of the **"flow"** concept named in the research brief.
2. **Communication at its core** — *"It's giving people everywhere the power to connect, collaborate, and do what's most important to them. Your app is a communication tool."*
3. **Content is king** — *"Be selective about chrome... Let content be front and center, with nothing to obscure or clutter the scene."* Includes a concrete example matching the research brief's expectation of an "action-oriented" design: *"Display pictures on the full screen. Let a tap on the screen display an action bar with the most common actions for the photo. The action bar disappears after a few seconds of inactivity."*
4. **Cinematic experience** — *"Infuse your application with fluid, natural gestures that make the screen feel expansive... it's much more effective and satisfying to move through a list by swiping across the screen instead of tapping a scroll bar."*
5. **Fluid workflow** — *"Anticipate each move and efficiently adapt to each response... Identify usage patterns and adapt your UI to them"* — an explicit call for adaptive/predictive UI behavior based on individual usage patterns (e.g., surfacing a "select both contacts" shortcut if a user frequently emails two specific people together).
6. **Efficient ergonomics** — thumb-reachability and one-handed-use guidance: *"people usually interact with their smartphones in portrait orientation using one hand... Place the most common actions on the bottom two-thirds of the screen because a thumb travels more easily."*

(A seventh, "Moments of charm," covers delight/personality and is less relevant to a finance app's core interaction model, so I've summarized rather than quoted it in full.)

**Well-documented — all six/seven principles directly quoted from the primary PDF**, not reconstructed from a secondary description.

The **"peek"** concept (paired with "flow" in the research brief) is documented as a specific gesture tied to **Back navigation** in drill-down hierarchies, not a separate top-level principle: quoted directly from "The basics" chapter, *"Back and peek behavior... Peek at the previous level by touching the Back button and dragging their finger to the right, allowing them to see the previous level's contents without leaving their current screen."* So "peek" is precisely: a **press-and-drag on the Back control that previews the parent screen without committing to navigation** — released without moving forward = stay; completed drag = navigate back. **Well-documented — directly quoted and precisely scoped**, correcting any looser assumption that "peek" is a generic system-wide swipe-preview gesture; in this document it is specifically the Back-button-drag interaction.

### (b) Concrete conventions

- **Navigation structure**: the document prescribes a small, named set of navigation patterns — tabs (up to four per action bar), drill-down/hierarchical navigation with the Back-and-peek behavior above, "tab and drill down" combinations, and explicitly-named "Custom or unstructured navigation" as a fallback category. Quoted: *"Use up to four tabs in an action bar"* and *"Include a Back button in an action bar at the [top/bottom]... A tab and drill down strategy allows you to combine both navigation approaches."* **Well-documented.**
- **The Action Bar**: a fixed, bottom-of-screen region (not a top menu bar — a direct structural contrast with every desktop system in this file), holding up to a handful of actions plus an optional **"signature action"** (the single most important/frequent action, visually elevated with a circular themed-color background above the bar). Quoted: *"An action bar is an area along the bottom of the screen... Avoid filling up an action bar just because there's room... Try and avoid placing more than three actions on a bar."* **Well-documented.**
- **Bezel gestures**: system-level gestures triggered from the physical screen edge/frame, explicitly stated to be automatic (apps don't implement them): wake device, display notifications, display the BlackBerry Hub, minimize applications, display keyboard, display an application menu. **Well-documented**, and explicitly flagged in the document as **platform-level, not app-level** — another point of non-transferability to a desktop app.
- **Content gestures**: scroll, select, "progress through a file," peek, open an action menu, zoom in/out, and move-an-item — a defined, closed gesture vocabulary rather than an open-ended one. **Well-documented.**
- **Spacing/measurement — "design units" (du)**: a resolution-independent layout unit is explicitly specified, quoted directly: *"A design unit (du) is a unit of length that simplifies the creation of layouts across devices that have different screen specifications... One design unit equals approximately 0.69 mm of screen space. BlackBerry chose 0.69 mm after careful consideration of current and future screen specifications and how well the length fit into the rhythm of our user interface."* Device-specific du-to-pixel conversion is given via a per-device "bucket" number and screen density table. This is a genuinely **precise, well-documented, primary-sourced spacing rule** — notably more concrete than anything found for QNX Photon (System 2) and more quantified than CUA's column-count rule (System 1(b)).
- **Typography**: quoted directly, *"Slate Pro Font is the preferred font for the BlackBerry 10 smartphones because it is elegant and legible... BlackBerry 10 uses medium, regular, and light font weights, as well as light italic type. BlackBerry 10 uses extra, extra small to large font sizes. The extra large and extra, extra large sizes are CSS standards for font scaling."* **Well-documented — directly quoted**, including the specific named typeface (Slate Pro) and its weight/size vocabulary.
- **Non-transferable conventions, explicitly flagged per the research brief's instruction**: this document has **no menu-bar concept** (the Action Bar is bottom-anchored and touch-only), **no keyboard-accelerator system** analogous to CUA/Apple/NeXTSTEP/BeOS Command-key shortcuts (the physical-keyboard section covers touch-sensitive keyboard *gestures*, e.g. swiping on the keys for cursor control, not modifier-key shortcuts), and no window-management model at all (BB10 apps are single-screen-hierarchy, not multi-window). Any use of this system's *conventions* (as opposed to its *interaction philosophy*) in a desktop personal-finance app would require translation, not direct adoption.

### (c) Sources and confidence

- Primary: **"BlackBerry 10 UI Guidelines,"** official PDF from BlackBerry/RIM developer site, https://developer.blackberry.com/devzone/files/design/bb10/UI_Guidelines_BlackBerry_10.pdf. Downloaded and converted locally with `pdftotext`; read the ~3,600-line extracted text directly, including the full "Key principles," "The basics" (navigation, back-and-peek, screen structure, design units), and "Audio and visual style" / "Typography" chapters. **Well-documented** for everything quoted above.
- I did not separately verify a claim of specific 2013-launch-era wording differing from this document's 10.3-refresh content — the document itself notes its visual-refresh changelog, so some quoted content (e.g., "Revised action bars," "Simplified app icon design") is explicitly later than the original 2013 launch; the "Key principles" chapter's content, by contrast, is not marked as version-specific and I'm treating it as the stable core philosophy. This distinction is worth flagging rather than presenting the whole document as uniformly dated to 2013.

# Merchant identification via a local, user-editable keyword dictionary, not cloud/ML lookup

Monarch identifies merchants using a hosted merchant/ML model with no local equivalent available to us. We considered leaving descriptions unnormalized (the status quo, but keeps noisy processor-prefixed text like "SQ *BLUE BOTTLE COF" as the permanent display name) versus building a true merchant-identification pass. Building one still had to answer *how* to identify merchants without cloud access: an offline ML/fuzzy-matching model (higher accuracy but a heavier dependency and non-trivial to bundle/update offline) versus a simple local keyword dictionary the user can extend. We chose a keyword dictionary — a `merchants` table mapping a keyword substring to a canonical name, seeded with a small curated list of common merchants/processors and freely editable by the user via a dedicated management screen — because it requires no cloud call or bundled model, is transparent and correctable when it gets something wrong, and keeps this consistent with the project's "entirely local, no cloud merchant lookup" stance (see Categorization Rule in CONTEXT.md).

We also had to decide whether identifying a merchant should rewrite the Transaction's stored `description` or live alongside it. Overwriting would break import-dedup, which fingerprints on a normalized `description` (ADR-0002) — re-importing the same statement after editing the merchant dictionary must not change a Transaction's fingerprint. We chose a separate nullable `merchant_name` column, populated once at Import time and left alone afterward (no retroactive re-matching when the dictionary changes), leaving `description` as the untouched raw source of truth for fingerprinting.

# Rule-driven "rename merchant" writes the same `merchant_name` field as dictionary matching, not a new field or the raw description

Monarch's transaction rules can, in addition to assigning a category, "automatically rename the merchant" for matching transactions. PesantMoney's Categorization Rule already had a narrower action surface (category assignment only) before the Merchant dictionary (ADR-0011) existed, and once that dictionary lands, a Transaction can already carry an identified name via its nullable `merchant_name` column, populated once at Import time from keyword matching.

Adding a rename action raised the same question ADR-0011 already answered for dictionary matching: where does the identified name live? We considered three options. First, overwrite the raw `description` — rejected for the same reason ADR-0011 rejected it: `description` is the fingerprinting input for import-dedup (ADR-0002), and mutating it on a rule match would change fingerprints on re-import and silently break dedup. Second, introduce a second field distinct from the dictionary's `merchant_name` (e.g. a `renamed_merchant` override) — rejected because it would force every downstream consumer (Transaction list/detail display, rule description-matching fallback logic) to check two optional fields and decide precedence, doubling the surface area for a concept that is, from the user's point of view, the same thing: "the name I see for this transaction instead of the raw import text."

We chose to have the rename action write to the same `merchant_name` field the Merchant dictionary populates. Both are just different sources for the same value — one automatic (dictionary keyword match), one explicit (a user-authored rule) — and a rule match is the more specific, user-intentional signal, so a rule's rename action always takes precedence over a dictionary match for the same Transaction. Like dictionary matching, the rename action fires once, at Import time, in the same pass as category assignment (`apply_categorization_rules`); it is not retroactively reapplied to existing Transactions when a rule's rename value changes, consistent with the Merchant dictionary's no-retroactive-rematch behavior. This keeps "the name shown for a Transaction" a single field with a single, well-ordered set of writers, and requires no changes to how `description` is used for fingerprinting.
